# Домашнее задание к занятию «Микросервисы: принципы»

## Задача 1. API Gateway

Для организации API Gateway рассмотрим следующие решения:

- NGINX
- Kong Gateway
- Traefik
- HAProxy

### Сравнение решений

| Возможность | NGINX | Kong | Traefik | HAProxy |
|---|---|---|---|---|
| Маршрутизация запросов | + | + | + | + |
| Проверка аутентификации | +/-  | + | +  | +/- |
| Терминация HTTPS | + | + | + | + |
| Балансировка нагрузки | + | + | + | + |
| Rate limiting | + | + | + | + |
| Динамическая конфигурация | +/-  | + | + | +/- |
| Интеграция с Kubernetes | + | + | + | + |
| Мониторинг и API управления | +/-  | + | + | + |
| Простота эксплуатации | + | +/- | + | + |
| Специализация на API Gateway | +/-  | + | + | +/-  |

### Выбор решения

Для данной задачи я бы выбрал Kong Gateway. **Kong Gateway**.

Kong изначально предназначен для работы в качестве API Gateway и предоставляет необходимые для данной задачи функции:

- маршрутизация запросов к нужному микросервису;
- проверка аутентификационной информации;
- терминация HTTPS;
- балансировка нагрузки;
- ограничение количества запросов;
- централизованное управление API;
- интеграция с Kubernetes;
- возможность расширения функциональности с помощью плагинов.

### Обоснование выбора

NGINX и HAProxy отлично подходят для reverse proxy, балансировки нагрузки и терминации HTTPS, но для полноценного API Gateway часть функций необходимо реализовывать дополнительными модулями или средствами внешних систем.

Traefik также хорошо подходит для микросервисной архитектуры и Kubernetes, особенно благодаря автоматическому обнаружению сервисов. Однако Kong предоставляет более широкий набор специализированных API Gateway-функций и механизмов аутентификации.

Поэтому для крупной микросервисной системы выбираю Kong Gateway, поскольку он позволяет централизовать маршрутизацию, безопасность и управление API.

## Задача 2. Брокер сообщений

Для организации обмена сообщениями между микросервисами рассмотрим:

- Apache Kafka
- RabbitMQ
- NATS JetStream
- ActiveMQ Artemis

### Сравнение брокеров

| Возможность | Apache Kafka | RabbitMQ | NATS JetStream | ActiveMQ Artemis |
|---|---|---|---|---|
| Кластеризация | + | + | + | + |
| Хранение сообщений на диске | +  | + | +  | + |
| Высокая скорость работы | + | + | + | + |
| Поддержка различных форматов сообщений | + | + | + | + |
| Разграничение прав доступа | + | + | + | + |
| Очереди сообщений | +  | + | + | + |
| Pub/Sub | + | + | + | + |
| Долговременное хранение | +  | + | + | + |
| Репликация | + | + | + | + |
| Горизонтальное масштабирование | +  | + | + | +  |
| Простота эксплуатации | +/-  | + | + | +/-  |
| Подходит для Event Streaming | +  | +/- | + | +/-  |

### Выбор решения

В качестве брокера сообщений выбираю RabbitMQ.
RabbitMQ соответствует всем требованиям задачи и при этом достаточно прост в эксплуатации.

Основные преимущества:
- поддержка кластеризации;
- сохранение сообщений на диск;
- подтверждение доставки сообщений;
- очереди сообщений;
- различные схемы маршрутизации;
- Pub/Sub;
- разграничение прав доступа;
- поддержка различных форматов сообщений;
- мониторинг через web-интерфейс;
- возможность работы в Docker и Kubernetes.

Рассмотрим следующею архитектуру stack взаимодействия:

```text
                 +-------------+
                 |  Service A  |
                 +------+------+
                        |
                        | Message
                        v
                 +-------------+
                 |  RabbitMQ   |
                 |   Cluster   |
                 +------+------+
                        |
          +-------------+-------------+
          |             |             |
          v             v             v
      +-------+     +-------+     +-------+
      |Queue A|     |Queue B|     |Queue C|
      +---+---+     +---+---+     +---+---+
          |             |             |
          v             v             v
      Service B     Service C     Service D
```

Сообщения можно сохранять на диск, а очереди настроить как durable. При использовании кластера RabbitMQ можно повысить отказоустойчивость системы.

Таким образом, RabbitMQ является наиболее подходящим вариантом для данной задачи, поскольку одновременно удовлетворяет всем заявленным требованиям:
